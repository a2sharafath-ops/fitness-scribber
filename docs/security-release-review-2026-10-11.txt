P1 — CONFIRMED CATALOGUE AUDIT EXPOSURE; PROPOSED FIX TESTED
pooling_submit_catalogue accepts a user-supplied manifest ID in a coach-owned
client's submission. pooling_read_catalogue_admin then uses that ID to return
whole matching release-event rows, including evidence_id and reason. There is
no release-operator requirement for those rows. Knowing a manifest ID lets an
ordinary coach fetch matching audit details through their own client.
Reproduced using the exact captured function bodies and entirely fictional
tables/data in isolated PGlite. No other coach's production records were queried.

supabase/schema_pooling_security.sql requires current, non-revoked, unexpired
release-operator authorization with an evidence reference for the events field.
Ordinary coaches retain their own submissions and receive events: []. Existing
client-ownership checks and operator matching-event behavior are preserved.
This deliberately changes the older catalogue UI's event visibility; it does
not grant anyone new release authority or affect prescriptions/scheduling.

P2 — SEVEN INTERNAL PREDICATES HAVE UNNECESSARY DIRECT EXECUTE
The proposed SQL revokes PUBLIC/anon/authenticated direct execution from the
seven predicates listed below. Their owner can still call them from SECURITY
DEFINER functions. None is named directly in the inspected RLS policies; policies
use pooling_linked and pooling_governed_client, both kept accessible.
Real nested helper definitions plus an athlete RLS policy were tested locally:
direct helper calls fail, classic linked-client reads succeed, and enabling the
governed flag still hides those classic records.

KEEP THE REQUIRED ENTRY POINTS
become_coach: invitation-gated onboarding.
redeem_invite: claim an unclaimed client using its invitation code.
is_admin: current profile role; referenced by 21 inspected policies.
delete_client_and_data: authenticated owning-coach check and atomic deletion.
pooling_linked / pooling_governed_client: athlete RLS predicates.
These require signed-in access; converting them blindly to SECURITY INVOKER
would change their behavior and may cause RLS recursion or permission failures.

RETAIN OTHER LEGACY ENTRY POINTS PENDING DEDICATED COMPATIBILITY REVIEW
The remaining pooling entry points have caller/owner/linked-client checks or
delegate to checked helpers. Test-workspace creation delegates to role,
allowlist, expiry and slot checks. This is a source/permission review, not a
complete adversarial integration test of that older subsystem. Its migrations
are not maintained here. The retained notices have not been suppressed.

FUTURE PRIVILEGES
The live default privileges still grant authenticated and anon execution on
new public functions created by postgres/supabase_admin. Existing grants do
not imply future functions will be protected. Every new RPC migration should
explicitly revoke PUBLIC/anon and grant only intended roles in one transaction.
A default-privilege change needs a separate coordinated migration review; it
has not been bundled into the narrow proposal or applied to managed roles.

PASSWORD PROTECTION
The organization is on Free. Supabase's leaked-password protection requires Pro
or above. This is a paid-plan decision, not an application code fix. No upgrade
or account policy change made. Other password/authentication controls remain.
