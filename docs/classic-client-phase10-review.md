# Phase 10 — Classic client workspace review

24 September 2026. Compared with the approved [client-page proposal](./client-page-proposal.md). This is a code and authenticated-browser review, not a study of trainer outcomes or a clinical validation.

| Review area | Result |
|---|---|
| Information architecture | One client shell has Overview, Training, Progress, Check-ins & load, Assessments, and Profile in a consistent order. Overview prepares for today; Training plans and records; Progress shows dated outcomes; Check-ins groups response and load; Assessments owns screening and formal tests; Profile owns stable details and dated goals/lifestyle. |
| Routes | The six client routes and their detail routes render in regression tests. Old `/command/:id` and `/monitor/:id` links redirect to Training and Check-ins with query and anchor intact. Old goal/lifestyle assessment URLs redirect to Profile. Legacy ACWR, monotony and strain URLs redirect to Training load while retaining query and anchor. |
| Data ownership | Client-scoped reads and writes are used in the workspace. Concern cards now require the linked booking to belong to the same client. Overview and Training share `ClientWorkoutFlow`, so they write the same workout rather than maintaining two records. The app-wide clipboard intentionally supports copying a prescription between clients. |
| Loading and failures | Backend load shows a loading state or a retryable error. Table failures stay visibly warned. Writes are queued so rapid edits persist in order; the workspace reports saving, saved or failed. Thrown network errors now surface instead of being console-only. Local storage failures also surface. A failed backend write keeps its warning until a successful reload; refresh will not silently replace unsaved local changes. |
| Accessibility | Routed destinations use links; current client section and Check-ins view have a text label and `aria-current="page"`. Existing modal focus handling, semantic history tables, keyboard focus styling and non-colour status copy remain. The legacy metric detail no longer shows a fixed green readiness icon. |
| Responsive layout | Authenticated browser checks at 390px and 768px found no page-wide horizontal overflow or visible client action below 44px. Phase 8 also checked the six main pages at 390px, 768px and 1280px. |
| Trainer flow and duplication | Overview prioritizes next session, concerns/reminders, check-in context and today's workout. Full planning stays in Training; strength and assessment outcomes stay in Progress; dated observations and history stay in their source sections. Detail pages link back to their owning section. The repeated client avatar was removed from the legacy metric detail because the shared shell already provides identity. In-progress set drafts survive route navigation in memory; changed prescriptions ask before discard. |

Defects fixed during this review: assessment history crash from an undefined route flag; generic Overview observation source labels; console-only save failures and unordered rapid writes; route-changing buttons in the client workspace; legacy metric redirects dropping query/anchor; cross-client lookup for a concern's associated booking; duplicate client identity and unconditional green readiness icon in metric detail; unguarded prescription closing and loss of in-progress set edits on client-route navigation.

Validation: `npm test` passes 15 focused regression tests; `npm run lint` and `npm run build` pass. The changed-prescription close prompt was also exercised in the authenticated browser: cancelling kept the temporary draft open and discarding closed it, without saving a record. The build reports a large JavaScript chunk warning, which is a performance follow-up rather than evidence of a route or workflow failure. No pooling-engine behavior or new clinical rules were added.

Still required before claiming full release acceptance: complete the [live Supabase check](./classic-client-live-supabase-check-2026-09-24.md), including the blocked Classic workout path and cleanup of its temporary client; a formal screen-reader and zoom/reflow pass; and the proposal's formative comparison with practising trainers. These checks cannot be inferred from code review or the browser layout checks. No production client records were changed in Phase 10.
