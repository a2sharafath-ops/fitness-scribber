Wearable security changes — local review, 11 October 2026

Status
Code is implemented locally. No SQL was executed, no functions were deployed,
and no changes were committed or pushed. wearable-security.proposed.sql is a
review proposal, deliberately outside the automatic migrations directory.

What changed
- Connect, complete, sync, metadata and disconnect require a signed-in coach
  who owns the client or the athlete linked to that client.
- Connection state is random, expires after ten minutes, and is stored as a
  hash. The callback stores the provider code once; it cannot save tokens.
- Completion requires the initiating user and proof kept in that browser tab.
  One conditional DELETE RETURNING consumes the pending request before exchange.
- Oura and Fitbit use S256 PKCE. WHOOP uses its documented confidential-client
  exchange, with the same state, browser-proof and user checks in this app.
- Callbacks use provider-specific redirect paths. Neither provider codes nor
  access/refresh tokens are returned to the frontend.
- Sync attributes data to the client's coach, including when an athlete syncs.
  Provider and database failures return sanitized errors instead of success.
- The browser reads connection metadata through wearable-connections only.

Database proposal
The proposed SQL creates a server-only table for short-lived OAuth requests.
It also removes known browser policies and browser table/column privileges on
wearable_tokens, retaining access for service_role. Per-client OAuth tokens
belong in this restricted storage; shared vendor secrets belong in server-side
function environment variables. Supabase's public URL and anon/publishable key
remain browser configuration, protected by authentication and database policies.

Before approving SQL, inspect existing grants, inherited roles, views and RPCs
that might expose either table. Check existing table names and dependencies.
This proposal intentionally fails if the request table already exists, rather
than silently accepting an unknown schema. The legacy functions_schema.sql
still contains browser-read policies: do not rerun it after hardening. Align the
bootstrap schema as part of the separately approved database rollout.

Validation and limits
173 tests pass; lint and production build pass. Security tests execute the Edge
Function handlers against database/provider doubles and test the browser helper.
They cover ownership, expiry, wrong proof/user, callback replay, provider mixup,
PKCE, invalid token responses and database failures. Tests simulate atomic delete
behavior; actual Postgres permissions/concurrency and live vendor exchanges have
not been exercised. Edge handlers are not checked by the frontend linter.
The suite reports existing Vite HMR port-in-use warnings while the local app is
running; these did not fail the tests.

The new connection flow will fail closed until the request table and matching
functions exist. Existing production behavior is unchanged by these local files.
Vendor reading field mappings/scopes still need real integration verification.
Ownership is checked before exchange and again before writes; those checks and
the writes are separate statements, not a database lock on client reassignment.
Strict concurrent-reassignment guarantees would need a separately reviewed RPC.
Concurrent refresh-token rotation also needs live vendor testing.
